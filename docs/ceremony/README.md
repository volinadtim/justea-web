# Чайная церемония: запись и лендинг

Отчёт агента justea-ceremony по задачам №8 (запись на церемонию) и №9 (лендинг
по SB7). Дата: **2026-11-06** (по заголовку HTTP `Date` сервера justea.ru;
локальные часы машины спешат на ~20 минут). Ветка: `agent/ceremony`.

## Что известно о церемонии (ответы пользователя 2026-11-06)

- **Город:** Санкт-Петербург.
- **Место:** клуб чайной культуры «Мойчай» (теперь Special Tea); точный адрес
  пользователь даст позже.
- **Формат:** только разовое посещение в небольшой группе. Смысл для гостя —
  познакомиться с людьми и приобщиться к культуре, а не пройти курс. Поэтому в
  текстах нет абонементов и обучения, зато есть знакомство за столом.
- **Цена:** 600 ₽ за участие + оплата чая.
- **Регина:** данных пока нет, стоят заглушки с TODO.
- **Почта:** домен justea будет позже; адрес через env, реальная отправка
  выключена.

## Как работает запись

`POST /api/ceremony`, JSON:

```json
{ "name": "Тимофей", "email": "tim@example.com", "contact": "@tim",
  "people": 2, "comment": "первый раз", "consent": true }
```

Ответы: `200 {ok:true,id}`, `422 {ok:false,errors:{…}}` (ошибки по полям),
`429` с `Retry-After` (лимит), `400` (не JSON), `413` (тело >16 КБ),
`405` на GET.

Правила валидации: имя 2–100 символов, почта обязательна и приводится к
нижнему регистру, контакт до 200 символов, участников 1–12, комментарий до
2000 символов, согласие обязательно.

Антиспам:

- **honeypot** — скрытое поле `website`. Если заполнено, сервер отвечает
  `200 {ok:true}`, но заявку не сохраняет и не отправляет письма: бот не должен
  понять, что его отсеяли. В логе остаётся `[ceremony] honeypot: …`.
- **rate limit** — 5 заявок с одного IP за 10 минут, счётчик в памяти процесса.
  IP берётся из `X-Forwarded-For` (перед контейнером стоит хостовый nginx).
  Приложение разворачивается одним контейнером, поэтому памяти достаточно;
  при нескольких инстансах счётчик нужно вынести в Redis.

**Работает без ключей.** Заявка пишется строкой JSON в
`$CEREMONY_DATA_DIR/ceremony-requests.jsonl` (по умолчанию `.data/` рядом с
`process.cwd()`). Если файл недоступен — заявка целиком уходит в лог процесса
(`docker logs`), и ответ всё равно `200`. Письма без ключа провайдера
печатаются в лог.

## Переменные окружения

Все необязательные, добавлены в `.env.example`:

| Переменная | Что делает |
|---|---|
| `CEREMONY_DATA_DIR` | Куда писать заявки. По умолчанию `.data` |
| `CEREMONY_MAIL_PROVIDER` | `resend` или `log`. **По умолчанию `log`** — письма только в лог, ничего не отправляется |
| `CEREMONY_MAIL_FROM` | Отправитель, например `Justea <ceremony@justea.ru>` |
| `CEREMONY_MAIL_TO` | Куда приходят заявки Регине. Не задан — уведомление не отправляется |
| `RESEND_API_KEY` | Ключ Resend |

Отправка по умолчанию выключена: пользователь решил 2026-11-06, что почта на
домене justea появится позже, адрес задаётся через env, реальных писем пока
быть не должно. Чтобы включить, нужно явно выставить
`CEREMONY_MAIL_PROVIDER=resend` и ключ.

Пока реализован один провайдер — **Resend**, по HTTP API через `fetch`, без
новых зависимостей. Если пользователь выберет Yandex 360 или другой SMTP,
понадобится `nodemailer` (новая зависимость в `package.json` — это чужая зона,
нужно решение оркестратора) и ещё одна ветка в `app/api/ceremony/mail.ts`:
интерфейс `Letter` + `deliver()` для этого и сделан.

- `npx tsc --noEmit` — чисто. `pnpm lint` — ошибки только в чужих файлах
  (`ThemeToggle`, `FavoriteButton`, `TeaBrewSection`, `BrewRatio/*`,
  `Search`, `ArrowHint`), они были до моих правок.
- `pnpm build` — проходит; `/ceremony` и `/ceremony/privacy` статические,
  `/api/ceremony` динамический.
- Валидная заявка → `200`, строка в `ceremony-requests.jsonl`, почта
  нормализована к нижнему регистру.
- Заявка без согласия, с плохой почтой, коротким именем и `people: 99` → `422`
  со всеми четырьмя ошибками сразу.
- Honeypot заполнен → `200`, заявки в файле нет, в логе `honeypot`.
- 6 заявок подряд с одного IP → шестая `429`.
- Каталог для заявок недоступен для записи → `200`, заявка в логе,
  `хранение log`.
- `GET /api/ceremony` → `405`, тело не-JSON → `400`.
- `/sitemap.xml` содержит `/ceremony`.

## Чего не хватает и кто должен дать

1. **Данные о Регине** — биография и фото. Видимые заглушки
   `CeremonyPlaceholder` с TODO в `app/ceremony/content.ts`, выдуманных фактов
   на странице нет. Остальное см. [open-questions.md](./open-questions.md).
2. **Точный адрес клуба**, длительность, размер группы, список чаёв и
   регулярность. Город и клуб уже известны и стоят в текстах.
3. **Почта** — провайдер, адрес отправителя, адрес Регины; пока отправка
   выключена по решению пользователя.
4. **Реквизиты оператора ПД** — страница политики помечена `noindex` и
   открывается с плашкой «черновик», пока не заполнены скобки. После
   заполнения нужно снять `robots: { index: false }` в
   `app/ceremony/privacy/page.tsx` и показать текст юристу.
5. **Финальные формулировки** — через агента justea-voice. Все тексты лендинга
   собраны в `app/ceremony/content.ts`, кроме блоков «Почему чай дома не такой»,
   «Если не прийти», «Сколько стоит» и герой — они лежат разметкой в
   `app/ceremony/page.tsx`; при передаче в voice их стоит тоже вынести в
   `content.ts`.
6. **Дизайн** — используются существующие токены (`--color-main*`, Bainsley,
   Comfortaa для цифр, `border-2`, размеры 50/37/22/19/14 px из
   `docs/design/README.md`). Отдельного макета лендинга нет: это зона агента
   justea-design.

## Нужно от инфраструктуры (чужая зона, предложение оркестратору)

В контейнере `process.cwd()` = `/app`, и пользователь `nextjs` не может там
создать каталог: заявки уйдут в лог и потеряются при пересборке. Чтобы заявки
жили между деплоями, в `infra/docker/docker-compose.yml` нужен том:

```yaml
    environment:
      - CEREMONY_DATA_DIR=/data
    volumes:
      - ceremony-data:/data

volumes:
  ceremony-data:
```

и в `infra/docker/Dockerfile` перед `USER nextjs`:

```dockerfile
RUN mkdir -p /data && chown nextjs:nodejs /data
```

Пока тома нет, заявки всё равно не теряются совсем: они видны в
`docker logs` и в письме Регине.
