## 1. `pu-erh` как тип чая расходится с обоими стандартами

### Что сейчас

```ts
export type TeaType = "green" | "black" | "oolong" | "pu-erh" | "white" | "yellow";
```

### Проблема

И ISO 20715:2023, и китайский GB/T 30766-2014 определяют шестой тип как **тёмный
чай** (dark tea / 黑茶). Пуэр — его **подтип**, а не самостоятельный тип:

> ISO 20715:2023, п. 5.6 Dark tea → 5.6.1 Ripen pu-erh tea, 5.6.2 Other dark teas

Следствия текущей схемы:
- Лю Бао (六堡茶, GB/T 32719.4), Фу Ча (茯茶, GB/T 32719.5), хэй ча Хунани
  (湘尖茶, 花卷茶) — тёмные чаи, но не пуэры. В каталоге их приходится помечать
  `pu-erh`, что неверно.
- В `docs/puerh-dark-tea-research.md` уже 45 записей, где хэй ча Хунани и Любао
  Гуанси проходят как `pu-erh`.
- **Шэн пуэр по технологии вообще не тёмный чай.** ISO 20715 называет подтипом
  тёмного чая только *ripen* (шу) пуэр. Молодой шэн — фиксация + скручивание +
  сушка на солнце, без ферментации в куче — по определению соответствует
  `sun-dried green tea` (п. 5.3.3), и только после многолетнего хранения
  приобретает признаки тёмного чая.

### Предложение

```ts
export type TeaType =
    | "green" | "black" | "oolong" | "white" | "yellow" | "dark";

/** Подтип по ISO 20715:2023, раздел 5 */
export type TeaSubtype =
    // black
    | "orthodox" | "broken" | "congou" | "souchong"
    // green
    | "pan-fired" | "roasted" | "sun-dried" | "steamed" | "broken-green" | "matcha"
    // white
    | "bud" | "bud-leaf"
    // dark
    | "ripen-puerh" | "other-dark";
```

Миграция: `pu-erh` → `dark`; шу → `subtype: "ripen-puerh"`; хэй ча и Любао →
`subtype: "other-dark"`. Для шэна — см. ниже, нужно решение.

### Варианты для шэн пуэра

| Вариант | Плюс | Минус |
|---|---|---|
| **A.** `type: "dark"`, `subtype: "other-dark"` | привычно пользователю, рядом с шу | расходится с ISO для молодого шэна |
| **B.** `type: "green"`, `subtype: "sun-dried"` для молодого; `"dark"` для выдержанного | строго по ISO | пользователь не найдёт молодой шэн в «пуэрах» |
| **C.** `type: "dark"` + новое поле `postFermentation: "none" \| "piled" \| "aged"` | и корректно, и находится | +1 поле |

**Рекомендую C.** Пуэр остаётся на месте в UI, а различие шэн/шу и молодой/выдержанный
выражено полем, которое прямо соответствует ISO 20715 п. 3.11 (piling fermentation).

### Если не менять

Каталог будет противоречить обоим стандартам, на которые сайт ссылается как на
источник. Для справочника, чья ценность в достоверности, это прямой удар по доверию.

**Источники:** ISO 20715:2023 п. 3.17, 5.6; GB/T 30766-2014 «茶叶分类»; серия
GB/T 32719 «黑茶»; GB/T 22111-2008 «普洱茶».

## 2. У каждого факта должен быть источник

### Проблема

Сейчас в схеме нет ни одного поля для источника. Проверить ни один факт нельзя.
Из 340 кандидатов в `docs/*.json` **ни один** не содержит поля источника,
а у 8 каталожных чаёв все параметры заваривания не подкреплены ничем.

### Предложение

Добавить опциональный тип и привязку:

```ts
export type SourceLevel = "A" | "B" | "C";
export type Confidence = "high" | "medium" | "low";

export interface SourceRef {
    /** id источника в docs/sources/catalog.json → sources */
    id: string;
    /** Точная привязка: «ISO 3103:2019, Table 1» */
    ref?: string;
}

export interface Sourced<T> {
    value: T;
    sources: SourceRef[];
    confidence: Confidence;
    /** Если источники расходятся — что именно и как решено */
    note?: string;
}
```

Минимальный вариант, не ломающий текущий JSON: добавить в `BrewMethod` и в `meta`
по одному опциональному полю `sources?: SourceRef[]`, а реестр источников держать в
`docs/sources/catalog.json` (уже готов: 34 источника, 31 из них уровня A).

### Что это даёт на сайте

На странице чая можно показать «откуда эти параметры» — это ровно то, чем
справочник отличается от блога. Уровень источника (A/B/C) можно показывать значком.

## 3. `ratio` и `infusions[].time` — одиночные числа, а источники дают диапазоны

### Проблема

```ts
ratio: number;                  // одно число
temperature: { from, to };      // диапазон — хорошо
infusions: { time: number }[];  // одно число
```

Температура уже диапазон, а навеска и время — нет. Но источники расходятся именно
по ним. Пример из выгрузки (официальные японские данные, уровень A):

| Сенча | Навеска | Температура | Время |
|---|---|---|---|
| высшая (上) | 3,3 г/100 мл | 70 °C | 120 с |
| обычная (並) | 2,2 г/100 мл | 90 °C | 60 с |
| сейчас в `data/teas.json` | 2,0 г/100 мл | 70–80 °C | один пролив |

Одним числом это не выражается: разница по навеске в 1,5 раза, по времени — в 2 раза,
и она привязана к грейду.

Ещё резче у гёкуро: **16,7 г/100 мл** против 2,2 у обычной сенчи — разница в 7,5 раза.
Если у гёкуро в каталоге окажется `ratio: 4` «по аналогии с зелёным чаем», это будет
грубая ошибка, которая испортит заварку пользователю.

### Предложение

```ts
export interface Range { from: number; to: number; }

export interface BrewMethod {
    // ...
    /** Гр чая на 100 мл воды; число — если источник даёт точку, Range — если диапазон */
    ratio: number | Range;
    temperature: Range;
    infusions: {
        number: number;
        time: number | Range;
        notes?: string;
    }[];
}
```

Обратная совместимость: `number` остаётся валидным, в UI — `typeof ratio === "number"
? ratio : \`${ratio.from}–${ratio.to}\``.

## 4. `meta.rating` — число без источника

### Проблема

```ts
meta: { rating: number; /* 1.0–5.0 */ }
```

У Лунцзина стоит `4.7`, у Те Гуань Инь — своё значение, и так далее. **Источника у
этих чисел нет и быть не может**: это не измеряемая величина. На справочном сайте,
который рядом показывает температуру и время, рейтинг выглядит как такой же
объективный параметр — а он взят из воздуха.

Это самая серьёзная проблема схемы с точки зрения достоверности: остальные поля
можно подкрепить источником, это — нельзя.

### Варианты

| Вариант | Что делать |
|---|---|
| **A.** Убрать поле | честно, но ломает сортировку и UI, если она есть |
| **B.** Переименовать в `popularity` и считать по данным сайта | честно, появляется смысл: число из аналитики |
| **C.** Оставить как `editorialRating` + подпись «оценка редакции» | честно, но нужно решить, кто редакция |
| **D.** Оставить как есть | ⚠ сайт публикует непроверяемые числа как факты |

**Нужно решение пользователя.** Я не меняю ни данные, ни UI.

То же касается `meta.favorite` — но это пользовательское состояние, оно в порядке
(хотя логичнее держать его в `localStorage`, а не в данных каталога; в
`data/teas.json` у `longjing` стоит `favorite: true`, то есть состояние одного
пользователя попало в общие данные).

## 5. Нет полей `processing` и `oxidation` — самых проверяемых свойств чая

### Проблема

И ISO 20715, и GB/T 30766 классифицируют чай **по технологии обработки**:

> «The basic tea types are classified based on the specific processing techniques used
> to control the extent of aeration and the characteristic quality features that are
> formed.» — ISO 20715:2023, п. 4

Технология — это то, что можно подтвердить стандартом. Вкусовые дескрипторы — нельзя.
При этом в схеме есть `aroma`, `flavor`, `aftertaste` (непроверяемые) и нет ни одного
поля про технологию (проверяемого).

### Предложение

```ts
export interface Tea {
    // ...
    subtype?: TeaSubtype;
    /** Степень аэрации в процентах или класс по ISO 20716 для улунов */
    oxidation?: Range | "light" | "medium" | "high";
    /** Ключевые процессы по ISO 20715 п. 3.3–3.11 */
    processing?: ("withering" | "tumbling" | "aeration" | "enzyme-inactivation"
                | "rolling" | "shaping" | "yellowing" | "piling-fermentation"
                | "drying" | "grinding")[];
    /** Сорт куста, если известен и закреплён стандартом */
    cultivar?: string;
}
```

Классы аэрации улуна (light / medium / high) — прямая норма ISO 20716:2022 п. 3.1,
Note 1. Для Те Гуань Инь привязка к классу — отраслевая практика (ISO не привязывает
классы к сортам), это нужно пометить `confidence: "low"`.

## 6. `liquorColor` — произвольный hex

### Проблема

```ts
liquorColor?: string;  // hex, например "#E6D7A8"
```

Откуда конкретный hex — неизвестно. Уровень A есть только для **словесного** описания:

> зелёный чай — «pale yellow-green to amber»; чёрный — «pale amber to deep
> brown/black» — ISO/TR 12591:2013, п. 3.2

Конкретный цвет настоя зависит от навески, времени, воды и толщины слоя — одного
правильного hex не существует.

### Варианты

| Вариант | Что делать |
|---|---|
| **A.** Оставить hex, подписать «иллюстративный цвет» | минимальная правка, честно |
| **B.** Добавить `liquorColorWords` по ISO/TR 12591 и GB/T 14487-2017 | +проверяемость |
| **C.** Измерять по фото настоя при стандартных условиях | дорого, зато данные свои |

Рекомендую **A + B**: hex для оформления, слова — как факт со ссылкой.

## 7. Дегустационный и потребительский режим — это разные вещи

### Проблема

`BrewMethodType` = `gongfu | western | grandpa | cold-brew | iced`. Все пять —
потребительские. Но самые авторитетные параметры, которые вообще существуют, —
дегустационные:

| Источник | Что это |
|---|---|
| ISO 3103:2019 | метод для **органолептических испытаний**, не для питья. Прямая оговорка в п. 1 |
| GB/T 23776-2018 | метод экспертной оценки (审评) |

Их нельзя показывать пользователю как «как заварить», но нужно хранить: это точка
отсчёта, с которой сверяются все остальные числа.

И наоборот: **потребительского стандарта гунфу не существует вообще** — ни в ISO,
ни в GB/T, ни в JAS. Числа вида «20 с, +5 с каждый пролив» — отраслевая практика
уровня B/C.

### Предложение

```ts
export type BrewMethodType =
    | "gongfu" | "western" | "grandpa" | "cold-brew" | "iced"
    | "sensory-iso3103"   // ISO 3103:2019 — только как референс
    | "sensory-gb23776";  // GB/T 23776 — только как референс

export interface BrewMethod {
    // ...
    /** consumer — показывать как рекомендацию; reference — как точку отсчёта */
    purpose: "consumer" | "reference";
}
```

В `docs/sources/catalog.json` → `brewing_reference` эти режимы уже описаны с
полными параметрами, дисклеймерами и уровнями доверия.

## 8. `meta.harvestDate` описывает партию, а не сорт

```ts
meta: { harvestDate?: string; }  // "2024-04-15"
```

Для справочника по сортам чая дата сбора — свойство конкретной партии в чьей-то
банке, а не свойство Лунцзина. Если поле остаётся, честнее переименовать в
`referenceHarvestSeason` и хранить сезон («первый сбор, начало апреля»), а не дату.

У Лунцзина сейчас стоит `"2024-04-15"` — к 2026 году это выглядит как устаревшие
данные, хотя сам чай никуда не делся.

## 9. Грейд — отдельное поле

Официальные японские данные разделяют 上 (высший) и 並 (обычный) грейд с **разными**
параметрами заваривания. Китайские GI-стандарты тоже задают грейды (у белого чая
白毫银针 / 白牡丹 / 寿眉 — это грейды внутри GB/T 22291, а не разные чаи).

Сейчас в схеме грейда нет, поэтому либо грейды становятся отдельными `slug`
(и каталог раздувается), либо параметры усредняются (и теряют точность).

```ts
export interface Tea {
    // ...
    /** Грейд, если источник разделяет параметры по грейдам */
    grade?: string;
}
```

Либо грейд как вариант внутри `brewMethods[]` — у японских чаёв различаются именно
параметры заваривания, а не описание чая.

## Ответ justea-seo по схеме пуэра

Отвечаю на предложение от 2026-11-07 (inbox #4). **Согласен с тремя пунктами из
четырёх, по двум есть оговорки.** Ничего из этого не блокирует работу — данные
можно добавлять.

### ✅ `type: "pu-erh"` как ключ маршрута — согласен

Ключ не переименовываем. Это ровно вариант (a), который я и рекомендовал, и он
подкреплён данными market: «пуэр» — 194 630 показов/мес, «тёмный чай» — 5 894,
«хэй ча» — 694. План Б с мапой `dark → "pu-erh"` не нужен: лишний слой
преобразования ради ключа, который и так нас устраивает.

**Важное уточнение от market, которое стоит зафиксировать в схеме комментарием:**
slug почти не влияет на ранжирование, а вот **название страницы для читателя —
влияет сильно**. Market прямо просит, чтобы «пуэр» оставалось главным словом в H1
и title; страница с основным именем «Тёмный чай» — потеря цели. Это не моя зона,
но раз схема фиксирует классификацию, пусть рядом будет и это ограничение.

### ✅ `standardCategory?: "dark"` — согласен, с уточнением типа

Поле правильное: оно и решает конфликт — ключ маршрута остаётся торговым,
классификация остаётся корректной.

Уточнение: сделать его не литералом `"dark"`, а полным перечислением шести типов
по стандарту, иначе поле нельзя будет использовать больше нигде:

```ts
/** Формальная категория по ISO 20715:2023 и GB/T 30766-2014.
 *  Заполняется только там, где расходится с `type`. */
standardCategory?: "green" | "black" | "oolong" | "white" | "yellow" | "dark";
```

Источник значений: ISO 20715:2023 п. 3.12–3.17, GB/T 30766-2014 «茶叶分类».
Сейчас расхождение единственное (`pu-erh` → `dark`), но поле пригодится и дальше:
например, Аньцзи байча (安吉白茶) по названию «белый чай», а по стандарту зелёный.

### ⚠️ `puerhKind?: "shu" | "sheng"` — согласен для пуэра, но не как общее решение

Для записей пуэра поле корректно, и оно действительно нужно: шу и шэн — атрибут
данных, а не отдельные типы, тут seo прав.

Оговорка: **имя поля привязано к одному чаю, а различие шире.** Любао (六堡茶),
фу чжуань (茯茶), хунаньские хэй ча — тоже постферментированные тёмные чаи, но не
пуэры, и значения `"shu" | "sheng"` к ним неприменимы. Когда они появятся в
каталоге (market подтверждает отдельный спрос: «хэй ча лю бао»), поле придётся
либо расширять, либо дублировать.

Нормативно различие выражается не через «шу/шэн», а через **процесс**:

| Значение | Что это | Источник |
|---|---|---|
| `"none"` | постферментации не было | — |
| `"piled"` | ферментация в куче (渥堆 / piling fermentation) | ISO 20715:2023 п. 3.11; GB/T 22111-2008 п. 4.3 |
| `"aged"` | длительное естественное старение | GB/T 22111 п. 4.3 называет исходным материалом постферментации и маоча, и готовый шэн |

Отображение: шу → `"piled"`, молодой шэн → `"none"`, выдержанный шэн → `"aged"`,
любао и фу чжуань → `"piled"`.

**Моё предложение — не блокирующее:** оставить `puerhKind` как есть (это честное
поле, оно действительно про пуэр и нужно для подписи в интерфейсе), а когда
дойдём до тёмных чаёв вне пуэра, добавить рядом `postFermentation`. Если удобнее
сделать сразу — я за, но настаивать не буду: сейчас в каталоге тёмных чаёв кроме
пуэра нет, и `puerhKind` ничего не ломает.

### ⚠️ `caution?: string` в `Tea` — место верное, тип я бы расширил

**Уровень согласен полностью:** сноска относится к чаю, а не к способу
заваривания. В `BrewMethod` ей делать нечего.

Оговорка по типу. `caution?: string` — это предложение о здоровье на странице
**без прослеживаемого источника**. Мы весь проект занимаемся обратным: я только
что убрал из текстов «чай натощак вызывает тошноту» именно потому, что источника
нет, а voice внёс это в таблицу запретов. Сноска без источника — та же проблема,
только в схеме.

Предлагаю:

```ts
caution?: {
    text: string;
    /** id источника в docs/sources/catalog.json → sources */
    sources: SourceRef[];
};
```

Если менять тип не хочется, минимальный компромисс: оставить `caution?: string`
в данных сайта, но **держать связку slug → источник в `docs/sources/catalog.json`**
(она уже есть: поле `caution` там хранит `text`, `sources`, `level` и `basis`) и
договориться, что любое изменение текста сноски проходит через меня. Тогда
прослеживаемость сохраняется хотя бы на уровне репозитория.

### Что нужно учесть при вводе данных — следствие из стандарта

Не вопрос схемы, но прямо влияет на заполнение, поэтому фиксирую здесь.

**По GB/T 22111-2008 категории «рассыпной шэн-пуэр» не существует.** Пункт 5.1:
рассыпным бывает **только шу**; прессованным — и шэн, и шу. Пункт 6.5.2: шэн
получается только после прессования (蒸压成型). Рассыпное сырьё до прессования —
это 晒青茶 (маоча), а не пуэр.

Следствие для данных: запись с `puerhKind: "sheng"` и без `pressedForm`
противоречит стандарту, на который мы же ссылаемся. Варианты: либо такие записи
не заводим, либо заводим с явной пометкой «по стандарту это маоча, а не пуэр».
Разбор — в [`raw/cn-gb-22111-puer.md`](./raw/cn-gb-22111-puer.md).

## 10. `postFermentation` — предложение созрело: четыре значения, а не три

Добавлено **2026-11-07**, после выгрузки источников по Любао и фу чжуаню
(задание из inbox #7). Полный разбор —
[`raw/cn-dark-liupao-futea.md`](./raw/cn-dark-liupao-futea.md).

В #5 мы договорились: `puerhKind` оставляем, а `postFermentation` вводим, когда
дойдём до Любао и фу чжуаня. Дошли. **И выяснилось, что трёх значений, которые я
предлагал раньше, не хватает.**

### Что говорят технологические цепочки из стандартов

| Чай | Нормативная цепочка | Механизм постферментации |
|---|---|---|
| Шэн-пуэр | фиксация → сушка на солнце → прессование → хранение | **только выдержка**, операции в цехе нет |
| Шу-пуэр | … → **渥堆** → … | **куча** (ускоренная микробная ферментация) |
| **Любао** | 筛选 → 拼配 → **渥堆** → 汽蒸 → прессование или нет → **陈化** → упаковка | **куча И выдержка** — две обязательные операции |
| **Фу чжуань** | 毛茶筛分 → 拼配 → **渥堆** → 汽蒸 → **发花** → сушка → упаковка | **发花** — намеренное выращивание гриба |

Источник цепочек Любао и фу чжуаня — Лю Чжунхуа 2019, Ключевая лаборатория
чаеведения Минобразования КНР; автор в числе разработчиков GB/T 32719.5-2018,
то есть первичный свидетель, уровень **A**.

### Почему `"none" | "piled" | "aged"` мало

1. **`发花` не описывается ни одним из трёх значений.** Это не куча и не
   выдержка, а культивирование *Eurotium cristatum*. У фу чжуаня количество
   этого гриба — **определяющий показатель** стандарта (с 2013 года, переведён
   из справочного), то есть по нему партию принимают или отклоняют. Другого
   такого чая в национальных стандартах КНР нет.
2. **У Любао механизма два, а не один.** 渥堆 и 陈化 — обе операции в цепочке.
   Записать Любао как `"piled"` — потерять выдержку; как `"aged"` — потерять кучу.

### Предложение

```ts
type PostFermentation =
  | "none"      // шэн-пуэр: постферментация только за счёт хранения
  | "piled"     // 渥堆 — шу-пуэр
  | "aged"      // 陈化 — обязательная выдержка как операция
  | "flowered"  // 发花 — культивирование Eurotium cristatum, фу чжуань

postFermentation?: PostFermentation[]   // массив: у Любао это ["piled", "aged"]
```

**Массив, а не одиночное значение** — ровно из-за Любао. Если массив не нравится,
альтернатива — одиночное значение плюс отдельный флаг `aged?: boolean`, но это
хуже: выдержка окажется не в том же измерении, что остальные механизмы, хотя
нормативно она такая же операция цепочки.

Заполнение по каталогу:

| slug | `postFermentation` |
|---|---|
| шэн-пуэры (`lao-banzhang`, `yiwu`, `bingdao`) | `["none"]` |
| шу-пуэры (`gongting-puer`, `menghai-shu`) | `["piled"]` |
| `tuocha` | `["piled"]` или `["none"]` — зависит от того, шу или шэн: точа это форма, а не тип |
| `liupao` | `["piled", "aged"]` |
| `fu-zhuan` | `["piled", "flowered"]` |

### Что это НЕ ломает

`puerhKind` остаётся как есть — решение из #5 в силе. Поля независимы:
`puerhKind` отвечает на вопрос «шу или шэн» для пуэра, `postFermentation` — на
вопрос «как именно постферментировали» для любого тёмного чая. У пуэра они
избыточны по отношению друг к другу, у Любао и фу чжуаня `puerhKind` просто
не заполняется.

### Оговорка про определения

**Нормативных определений терминов 渥堆 и 陈化 я не подтвердил.** В выгруженной
части раздела «термины и определения» GB/T 32719.4 их нет, сами операции названы
только в цепочке. Определения, скорее всего, лежат в **GB/T 32719.1-2016
«黑茶 第1部分：基本要求»** — если понадобится точная терминология для подписей на
сайте, это следующий шаг.

## 11. Варка как метод заваривания — поле уже есть, нужен ключ

Решение оркестратора из inbox #7: варку пуэра описываем, она ложится третьим
методом в существующий механизм `data/teas.json`, новый облик не нужен.

С моей стороны требуется только одно — договориться о ключе метода. Сейчас в
данных `gongfu-N` и `western-N`. Предлагаю **`boiled-N`**.

Основание: DB53/T 236-2007 делит способы ровно на два, и варка (煮茶法) —
полноправный второй, с отдельным разделом 6 и своими параметрами (30–60 с,
соотношение 1:40–1:60, посуда 壶（锅）). Данные —
[`priority-teas.json`](./priority-teas.json) →
`common_puer_facts.provincial_brewing_standard.boiled_method`.

⚠ **Чего в источнике нет:** привязки варки к подтипу. Раздел 6 написан для пуэра
в целом, фразы «варят только шу и выдержанный шэн» в стандарте нет. Не утверждать.

⚠ **И правило употребления то же:** стандарт отменён 2026-01-29, поэтому «до
2026 года способ был закреплён местным стандартом Юньнани», а не «по стандарту
заваривают так».

### Навеска разнесена по методам

По решению оркестратора (inbox #7) 1,7–2,5 и 5–7 г/100 мл больше не сводятся в
один диапазон:

| Метод | Навеска | Уровень |
|---|---|---|
| `western` | **1,7–2,5 г/100 мл** (1:40–1:60) | DB53/T 236 п. 5.2.8, `medium` |
| `gongfu` | **5–7 г/100 мл** | `derived` + `practice`, действующего источника нет |
| `boiled` | **1,7–2,5 г/100 мл** (1:40–1:60) | DB53/T 236 п. 6.2.7, `medium` |

Диапазон «от 1,7 до 7» не описывает ни один из трёх способов — поэтому они
разнесены, а не усреднены.

## 12. `commonMistakes` — поле для seo, и материал под него уже собран

Запрос justea-seo, передан оркестратором (inbox #8) как единственное, что сейчас
нужно от меня по схеме.

### Что это за поле и почему оно моё

`commonMistakes` — короткие записи «что обычно думают про этот чай неверно». Для
seo это ответы на вопросные запросы, для voice — безопасный способ говорить
содержательно, не уходя в тему пользы. А для меня это **естественный выход
накопленного**: за пять этапов набралось много случаев, где самое
распространённое утверждение о чае не подтверждается источниками, и до сих пор
они лежали россыпью по разным файлам.

Главное условие, без которого поле вредно: **у опровержения должен быть источник
того же уровня, что у любого другого факта.** «Это миф» без ссылки — такое же
неподтверждённое утверждение, как и сам миф, только с обратным знаком.

### Предложение по типу

```ts
type CommonMistake = {
  claim: string            // расхожее утверждение, как его обычно формулируют
  correction: string       // что на самом деле, одним-двумя предложениями
  sources: SourceRef[]     // обязательно, тот же SourceRef, что у остальных фактов
  kind: "classification" | "origin" | "processing" | "composition" | "brewing"
}

commonMistakes?: CommonMistake[]
```

`kind` — чтобы seo мог группировать и чтобы в вёрстке можно было отличить
«путают категорию» от «путают параметры заваривания».

**Чего в типе сознательно нет:** поля вроде `severity` или `isMyth`. Мы не
оцениваем, насколько заблуждение серьёзно, и не навешиваем ярлык «миф» —
показываем утверждение, поправку и источник.

### Готовый материал: 12 записей с источниками

Все до единой опираются на уже выгруженные источники. Беру только то, где
опровержение имеет уровень A или B.

| Чай | Расхожее утверждение | Поправка | Уровень |
|---|---|---|---|
| пуэр | «бывает рассыпной шэн-пуэр» | По GB/T 22111 рассыпным бывает только шу; шэн становится пуэром лишь после прессования. Рассыпное сырьё — это 晒青茶, маоча | **A** |
| пуэр | «пуэр — отдельный, седьмой тип чая» | По ISO 20715 и GB/T 30766 типов шесть, пуэр относится к тёмным (dark) | **A** |
| гунтин | «гунтин — особый сорт пуэра» | Слово 宫廷 в GB/T 22111 не встречается вообще: это торговое название, соответствующее грейду 特级 | **A** |
| Бин Дао | «Бин Дао из Сишуанбаньны» | По приложению A GB/T 22111 Бин Дао — Линьцан, посёлок Мэнку | **A** |
| молочный улун | «молочный улун — это сорт чая» | Сорт называется Цзинь Сюань (台茶12號); «молочный улун» — торговое имя. Сорт пригоден и для баочжуна, и для красного чая | **A** |

| габа-чай | «габа — сорт чая» | Это способ обработки: 佳葉龍茶只是一種製茶技術的改良，而非特殊茶種. Габа-чай делают из зелёного, улуна, Цзинь Сюаня, Те Гуань Инь | **A** |

| гёкуро | «гёкуро заваривают как обычный зелёный чай» | Официальные японские параметры — 16,7 г/100 мл при 50 °C, то есть в 7,5 раза больше навески сенчи при вдвое меньшей температуре | **A** |

| матча | «матчу заваривают» | Матчу взбивают, порошок остаётся во взвеси (ISO/TR 21380 п. 4.2). Проливов нет ни одного — поэтому и модель данных под неё другая |**A** |

### Где взять данные

Все записи уже лежат в [`priority-teas.json`](./priority-teas.json) и
[`catalog.json`](./catalog.json) — в полях `disagreement`, `trap`,
`not_confirmed`, `do_not_confuse`, `key_finding`, `practical_implication`. Если
поле примут, я соберу их в один машиночитаемый файл
`docs/sources/common-mistakes.json` в формате выше, чтобы seo не выбирал их
вручную. Отдельного решения пользователя для этого не нужно — скажите, и сделаю.

### Связь с реестром отклонённых утверждений

Есть симметричный, но **другой** список — [`rejected-claims.md`](./rejected-claims.md):
утверждения, которые мы проверили и решили **не писать вообще**, потому что
опровержения у них тоже нет. Их в `commonMistakes` помещать нельзя: «источника
нет ни у утверждения, ни у его опровержения» — это не поправка, а молчание.

Разница на примере: «в гёкуро мало кофеина» идёт в `commonMistakes` (есть
измерение, которое это опровергает), а «в ходзиче меньше кофеина из-за обжарки» —
в `rejected-claims` (измерений нет ни за, ни против; известно только, что обжарка
меняет катехины).
