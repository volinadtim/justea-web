## 1. `pu-erh` как тип чая расходится с обоими стандартами

### Что сейчас

```ts
export type TeaType = "green" | "black" | "oolong" | "pu-erh" | "white" | "yellow";
```

### Проблема

И ISO 20715:2023, и китайский GB/T 30766-2014 определяют шестой тип как **тёмный
чай** (dark tea / 黑茶). Пуэр — его **подтип**, а не самостоятельный тип:

> ISO 20715:2023, п. 5.6 Dark tea → 5.6.1 Ripen pu-erh tea, 5.6.2 Other dark teas

Следствия текущей схемы:
- Лю Бао (六堡茶, GB/T 32719.4), Фу Ча (茯茶, GB/T 32719.5), хэй ча Хунани
  (湘尖茶, 花卷茶) — тёмные чаи, но не пуэры. В каталоге их приходится помечать
  `pu-erh`, что неверно.
- В `docs/puerh-dark-tea-research.md` уже 45 записей, где хэй ча Хунани и Любао
  Гуанси проходят как `pu-erh`.
- **Шэн пуэр по технологии вообще не тёмный чай.** ISO 20715 называет подтипом
  тёмного чая только *ripen* (шу) пуэр. Молодой шэн — фиксация + скручивание +
  сушка на солнце, без ферментации в куче — по определению соответствует
  `sun-dried green tea` (п. 5.3.3), и только после многолетнего хранения
  приобретает признаки тёмного чая.

### Предложение

```ts
export type TeaType =
    | "green" | "black" | "oolong" | "white" | "yellow" | "dark";

/** Подтип по ISO 20715:2023, раздел 5 */
export type TeaSubtype =
    // black
    | "orthodox" | "broken" | "congou" | "souchong"
    // green
    | "pan-fired" | "roasted" | "sun-dried" | "steamed" | "broken-green" | "matcha"
    // white
    | "bud" | "bud-leaf"
    // dark
    | "ripen-puerh" | "other-dark";
```

Миграция: `pu-erh` → `dark`; шу → `subtype: "ripen-puerh"`; хэй ча и Любао →
`subtype: "other-dark"`. Для шэна — см. ниже, нужно решение.

### Варианты для шэн пуэра

| Вариант | Плюс | Минус |
|---|---|---|
| **A.** `type: "dark"`, `subtype: "other-dark"` | привычно пользователю, рядом с шу | расходится с ISO для молодого шэна |
| **B.** `type: "green"`, `subtype: "sun-dried"` для молодого; `"dark"` для выдержанного | строго по ISO | пользователь не найдёт молодой шэн в «пуэрах» |
| **C.** `type: "dark"` + новое поле `postFermentation: "none" \| "piled" \| "aged"` | и корректно, и находится | +1 поле |

**Рекомендую C.** Пуэр остаётся на месте в UI, а различие шэн/шу и молодой/выдержанный
выражено полем, которое прямо соответствует ISO 20715 п. 3.11 (piling fermentation).

### Если не менять

Каталог будет противоречить обоим стандартам, на которые сайт ссылается как на
источник. Для справочника, чья ценность в достоверности, это прямой удар по доверию.

**Источники:** ISO 20715:2023 п. 3.17, 5.6; GB/T 30766-2014 «茶叶分类»; серия
GB/T 32719 «黑茶»; GB/T 22111-2008 «普洱茶».

## 2. У каждого факта должен быть источник

### Проблема

Сейчас в схеме нет ни одного поля для источника. Проверить ни один факт нельзя.
Из 340 кандидатов в `docs/*.json` **ни один** не содержит поля источника,
а у 8 каталожных чаёв все параметры заваривания не подкреплены ничем.

### Предложение

Добавить опциональный тип и привязку:

```ts
export type SourceLevel = "A" | "B" | "C";
export type Confidence = "high" | "medium" | "low";

export interface SourceRef {
    /** id источника в docs/sources/catalog.json → sources */
    id: string;
    /** Точная привязка: «ISO 3103:2019, Table 1» */
    ref?: string;
}

export interface Sourced<T> {
    value: T;
    sources: SourceRef[];
    confidence: Confidence;
    /** Если источники расходятся — что именно и как решено */
    note?: string;
}
```

Минимальный вариант, не ломающий текущий JSON: добавить в `BrewMethod` и в `meta`
по одному опциональному полю `sources?: SourceRef[]`, а реестр источников держать в
`docs/sources/catalog.json` (уже готов: 34 источника, 31 из них уровня A).

### Что это даёт на сайте

На странице чая можно показать «откуда эти параметры» — это ровно то, чем
справочник отличается от блога. Уровень источника (A/B/C) можно показывать значком.

## 3. `ratio` и `infusions[].time` — одиночные числа, а источники дают диапазоны

### Проблема

```ts
ratio: number;                  // одно число
temperature: { from, to };      // диапазон — хорошо
infusions: { time: number }[];  // одно число
```

Температура уже диапазон, а навеска и время — нет. Но источники расходятся именно
по ним. Пример из выгрузки (официальные японские данные, уровень A):

| Сенча | Навеска | Температура | Время |
|---|---|---|---|
| высшая (上) | 3,3 г/100 мл | 70 °C | 120 с |
| обычная (並) | 2,2 г/100 мл | 90 °C | 60 с |
| сейчас в `data/teas.json` | 2,0 г/100 мл | 70–80 °C | один пролив |

Одним числом это не выражается: разница по навеске в 1,5 раза, по времени — в 2 раза,
и она привязана к грейду.

Ещё резче у гёкуро: **16,7 г/100 мл** против 2,2 у обычной сенчи — разница в 7,5 раза.
Если у гёкуро в каталоге окажется `ratio: 4` «по аналогии с зелёным чаем», это будет
грубая ошибка, которая испортит заварку пользователю.

### Предложение

```ts
export interface Range { from: number; to: number; }

export interface BrewMethod {
    // ...
    /** Гр чая на 100 мл воды; число — если источник даёт точку, Range — если диапазон */
    ratio: number | Range;
    temperature: Range;
    infusions: {
        number: number;
        time: number | Range;
        notes?: string;
    }[];
}
```

Обратная совместимость: `number` остаётся валидным, в UI — `typeof ratio === "number"
? ratio : \`${ratio.from}–${ratio.to}\``.

## 4. `meta.rating` — число без источника

### Проблема

```ts
meta: { rating: number; /* 1.0–5.0 */ }
```

У Лунцзина стоит `4.7`, у Те Гуань Инь — своё значение, и так далее. **Источника у
этих чисел нет и быть не может**: это не измеряемая величина. На справочном сайте,
который рядом показывает температуру и время, рейтинг выглядит как такой же
объективный параметр — а он взят из воздуха.

Это самая серьёзная проблема схемы с точки зрения достоверности: остальные поля
можно подкрепить источником, это — нельзя.

### Варианты

| Вариант | Что делать |
|---|---|
| **A.** Убрать поле | честно, но ломает сортировку и UI, если она есть |
| **B.** Переименовать в `popularity` и считать по данным сайта | честно, появляется смысл: число из аналитики |
| **C.** Оставить как `editorialRating` + подпись «оценка редакции» | честно, но нужно решить, кто редакция |
| **D.** Оставить как есть | ⚠ сайт публикует непроверяемые числа как факты |

**Нужно решение пользователя.** Я не меняю ни данные, ни UI.

То же касается `meta.favorite` — но это пользовательское состояние, оно в порядке
(хотя логичнее держать его в `localStorage`, а не в данных каталога; в
`data/teas.json` у `longjing` стоит `favorite: true`, то есть состояние одного
пользователя попало в общие данные).

## 5. Нет полей `processing` и `oxidation` — самых проверяемых свойств чая

### Проблема

И ISO 20715, и GB/T 30766 классифицируют чай **по технологии обработки**:

> «The basic tea types are classified based on the specific processing techniques used
> to control the extent of aeration and the characteristic quality features that are
> formed.» — ISO 20715:2023, п. 4

Технология — это то, что можно подтвердить стандартом. Вкусовые дескрипторы — нельзя.
При этом в схеме есть `aroma`, `flavor`, `aftertaste` (непроверяемые) и нет ни одного
поля про технологию (проверяемого).

### Предложение

```ts
export interface Tea {
    // ...
    subtype?: TeaSubtype;
    /** Степень аэрации в процентах или класс по ISO 20716 для улунов */
    oxidation?: Range | "light" | "medium" | "high";
    /** Ключевые процессы по ISO 20715 п. 3.3–3.11 */
    processing?: ("withering" | "tumbling" | "aeration" | "enzyme-inactivation"
                | "rolling" | "shaping" | "yellowing" | "piling-fermentation"
                | "drying" | "grinding")[];
    /** Сорт куста, если известен и закреплён стандартом */
    cultivar?: string;
}
```

Классы аэрации улуна (light / medium / high) — прямая норма ISO 20716:2022 п. 3.1,
Note 1. Для Те Гуань Инь привязка к классу — отраслевая практика (ISO не привязывает
классы к сортам), это нужно пометить `confidence: "low"`.

## 6. `liquorColor` — произвольный hex

### Проблема

```ts
liquorColor?: string;  // hex, например "#E6D7A8"
```

Откуда конкретный hex — неизвестно. Уровень A есть только для **словесного** описания:

> зелёный чай — «pale yellow-green to amber»; чёрный — «pale amber to deep
> brown/black» — ISO/TR 12591:2013, п. 3.2

Конкретный цвет настоя зависит от навески, времени, воды и толщины слоя — одного
правильного hex не существует.

### Варианты

| Вариант | Что делать |
|---|---|
| **A.** Оставить hex, подписать «иллюстративный цвет» | минимальная правка, честно |
| **B.** Добавить `liquorColorWords` по ISO/TR 12591 и GB/T 14487-2017 | +проверяемость |
| **C.** Измерять по фото настоя при стандартных условиях | дорого, зато данные свои |

Рекомендую **A + B**: hex для оформления, слова — как факт со ссылкой.

## 7. Дегустационный и потребительский режим — это разные вещи

### Проблема

`BrewMethodType` = `gongfu | western | grandpa | cold-brew | iced`. Все пять —
потребительские. Но самые авторитетные параметры, которые вообще существуют, —
дегустационные:

| Источник | Что это |
|---|---|
| ISO 3103:2019 | метод для **органолептических испытаний**, не для питья. Прямая оговорка в п. 1 |
| GB/T 23776-2018 | метод экспертной оценки (审评) |

Их нельзя показывать пользователю как «как заварить», но нужно хранить: это точка
отсчёта, с которой сверяются все остальные числа.

И наоборот: **потребительского стандарта гунфу не существует вообще** — ни в ISO,
ни в GB/T, ни в JAS. Числа вида «20 с, +5 с каждый пролив» — отраслевая практика
уровня B/C.

### Предложение

```ts
export type BrewMethodType =
    | "gongfu" | "western" | "grandpa" | "cold-brew" | "iced"
    | "sensory-iso3103"   // ISO 3103:2019 — только как референс
    | "sensory-gb23776";  // GB/T 23776 — только как референс

export interface BrewMethod {
    // ...
    /** consumer — показывать как рекомендацию; reference — как точку отсчёта */
    purpose: "consumer" | "reference";
}
```

В `docs/sources/catalog.json` → `brewing_reference` эти режимы уже описаны с
полными параметрами, дисклеймерами и уровнями доверия.

## 8. `meta.harvestDate` описывает партию, а не сорт

```ts
meta: { harvestDate?: string; }  // "2024-04-15"
```

Для справочника по сортам чая дата сбора — свойство конкретной партии в чьей-то
банке, а не свойство Лунцзина. Если поле остаётся, честнее переименовать в
`referenceHarvestSeason` и хранить сезон («первый сбор, начало апреля»), а не дату.

У Лунцзина сейчас стоит `"2024-04-15"` — к 2026 году это выглядит как устаревшие
данные, хотя сам чай никуда не делся.

## 9. Грейд — отдельное поле

Официальные японские данные разделяют 上 (высший) и 並 (обычный) грейд с **разными**
параметрами заваривания. Китайские GI-стандарты тоже задают грейды (у белого чая
白毫银针 / 白牡丹 / 寿眉 — это грейды внутри GB/T 22291, а не разные чаи).

Сейчас в схеме грейда нет, поэтому либо грейды становятся отдельными `slug`
(и каталог раздувается), либо параметры усредняются (и теряют точность).

```ts
export interface Tea {
    // ...
    /** Грейд, если источник разделяет параметры по грейдам */
    grade?: string;
}
```

Либо грейд как вариант внутри `brewMethods[]` — у японских чаёв различаются именно
параметры заваривания, а не описание чая.
